# /brainstorm — Задача → Как сейчас → План → Задача разработчику

Скилл для аналитика: понять запрос (ошибка или доработка), разобрать, как это реализовано в конфигурации сейчас,
найти похожие задачи и как их сделали, и подготовить задачу в Jira, по которой разработчик реализует изменение
без дополнительных вопросов.

## Философия

- **Только чтение.** Никаких правок файлов, загрузок в базу, изменений данных
- **Доказательства, а не догадки.** Каждый вывод — со ссылкой на код, метаданные, результат запроса или задачу Jira
- **Одна точка согласования** — черновик задачи. До неё — вопросы и исследование, после «ок» — создание задачи
- **Задача для разработчика**: что и где менять, в каком порядке, как проверить. Не готовый код

## Где искать (кратко; подробно — раздел «Где искать конфигурацию и код» в CLAUDE.md)

| Что | Порядок |
|---|---|
| Код модулей (объект, менеджер, общий модуль, формы) | 1c-rag → Grep `*.bsl` по `configuration\` и `.formbin-cache\` |
| Общие формы, подписки, регл. задания, модуль приложения, `Template.txt` | Только выгрузка (в 1c-rag их нет) |
| Обычная форма: элементы, страницы, какая кнопка вызывает какую процедуру | `/form-bin` (overview / events) |
| Управляемая форма | `/inspect` form-info |
| Отчёт на СКД: запрос, поля, вычисления, варианты | `/inspect` skd-info (`overview` → `trace -Name <поле>` → `query`) |
| Печатная форма MXL | `/inspect` mxl-info + процедура заполнения в модуле (`ПолучитьМакет("<Имя>")`) |
| Права и меню | `/inspect` role-info; Grep по `Interfaces\*\Ext\Interface.bin` |
| Данные | `query_sql` + `/1c-sql-structure` |
| Логика в хранимой процедуре SQL (в коде `exec [dbo].[...]`, `МодульSQL.ВыполнитьЗапрос`) | `query_sql`: `OBJECT_DEFINITION`, `sys.sql_expression_dependencies` — см. `/1c-sql-structure` |

Если кеш `.formbin-cache` отсутствует или старше выгрузки — обнови его (`form-bin-export.ps1`, см. `/form-bin`).
Поведение методов платформы проверяй по справке синтаксиса: `bslsyntax_get_details` (точное имя), `bslsyntax_search_method` / `bslsyntax_search_global_function` / `bslsyntax_search_property` (по описанию).
Если MCP-сервер недоступен — **скажи явно** и продолжай с тем, что есть. Не подменяй источник молча.

## Процесс

### Фаза 0 — Вход

- Ключ Jira (`ABC-123`): `jira_get_issue` (описание, комментарии, связи), скриншоты — `jira_get_issue_images`
- Текст: работай с ним
- `diagnose_database` — индекс доступен
- Определи **тип запроса**: **Ошибка** (работает не так, как должно) или **Доработка** (нужно новое поведение). От типа зависят Фазы 1 и 5

### Фаза 1 — Уточнение (диалог)

Вопросы **по одному** через AskUserQuestion, с вариантами где возможно. Только то, чего нельзя найти самому.

Ошибка:
- Симптом (текст ошибки / неверная сумма / нет записи / медленно)
- Где воспроизводится: объект, форма, документ (номер, дата), пользователь/роль, ТСД или ПК
- Ожидаемое поведение и на чём основано
- С какого момента: всегда / после обновления / на части данных

Доработка:
- Бизнес-цель: какую проблему решает, кто пользователь (роль, рабочее место — ТСД, АРМ, ПК)
- Что должно происходить: входные данные, результат, где пользователь это видит
- Границы: что точно не меняем, есть ли образец («как в отчёте X»)
- Сроки/приоритет — только если влияет на объём (MVP или полностью)

**Остановись, когда картина ясна.**

### Фаза 2 — Как реализовано сейчас (только чтение)

1. **Объекты**: `search_1c_objects` → `get_object_metadata` (реквизиты, ТЧ, движения, связи). Не нашлось — Glob по `configuration\**\<Имя>.xml`
2. **Точка входа пользователя**: форма/команда/кнопка, с которой начинается сценарий. Для обычной формы — `/form-bin <путь> -Mode events`: кнопка → процедура
3. **Логика**: обработчики (`ОбработкаПроведения`, `ПередЗаписью`, `ПриОткрытии`, обработчики кнопок) через `list_object_modules` → `find_procedure_code`
4. **Цепочка вызовов**: `analyze_procedure_calls` до места, где формируется результат (или куда нужно встроить новое поведение)
5. **Фоновые и неявные вызовы**: подписки на события (`EventSubscriptions\*.xml`), регламентные задания (`ScheduledJobs\*.xml`), `Выполнить()` с кодом из `Template.txt` — Grep по выгрузке
5a. **Логика в SQL**: если цепочка доходит до `exec [dbo].[...]` / `МодульSQL.ВыполнитьЗапрос` — прочитай текст процедуры (`OBJECT_DEFINITION`, длинные — `SUBSTRING` по 8000), её зависимости (`sys.sql_expression_dependencies`) и кто ещё в SQL пишет в те же view. В выводах указывай, что текст из preprod, и `modify_date`
6. **Отчёты**: СКД — `/inspect` skd-info; без СКД — модуль объекта + макет
7. **Данные** (если применимо): таблицы через `/1c-sql-structure`, `SELECT TOP N ...` по конкретному документу/элементу
8. **Влияние**: `find_object_references`, `search_by_relationship` — кто ещё использует то, что будет меняться
9. **Свежесть**: при сомнениях сверь ключевой фрагмент с файлами выгрузки

Фиксируй находки ссылками `Обработка.АРМУпаковки → МодульФормы_Форма → КнопкаУпаковатьНажатие` с фрагментом кода (5–15 строк).

### Фаза 3 — Похожие задачи и образцы

1. **Jira**: `jira_search` (JQL `text ~ "<объект/ключевые слова>"`, сначала закрытые: `statusCategory = Done ORDER BY updated DESC`) — 3–5 самых похожих
2. По каждой подходящей: `jira_get_issue` (что просили, как решили), `jira_get_issue_development_info` (ветки/коммиты/PR, если подключены)
3. **Образец в коде**: `find_similar_procedures` / `search_procedures_direct` — где подобное уже сделано (разработчик повторит подход)
4. Открытые задачи по тем же объектам — кандидаты в дубли или конфликты (покажешь в Фазе 5)

Если похожих задач нет — так и скажи, не притягивай нерелевантные.

### Фаза 4 — Вывод

```markdown
## Анализ: <краткое название>

**Тип:** Ошибка / Доработка
**Как сейчас:** <2–5 предложений: сценарий и где он реализован>
**Причина / Что нужно изменить:** <1–3 предложения> — [установлено | гипотеза, уверенность: высокая/средняя/низкая]
**Доказательства:** <ссылки на код, метаданные, запросы>
**Похожие задачи:** <KEY — чем похожа, как решили> | нет
**Нужна доработка?** Да / Нет — настройки / данные / ожидаемое поведение
```

Доработка не нужна — объясни, что сделать пользователю, и заверши без задачи.

### Фаза 5 — Черновик задачи (ЕДИНСТВЕННАЯ точка согласования)

1. Дубли: открытые задачи из Фазы 3 — если есть похожая, покажи и спроси: дополнить комментарием или создать новую
2. Уточни (если неизвестно): проект Jira, тип задачи, связь с исходной
3. Покажи **полный текст задачи одним сообщением**:

```markdown
**Проект:** <KEY>   **Тип:** <Bug / Task / Story>   **Связь:** <relates to ABC-123>
**Заголовок:** <Объект: что сделать/исправить — до 80 символов>

### Контекст

### Как сейчас

### Что нужно
<Целевое поведение глазами пользователя. Для ошибки — причина: где в коде и почему; гипотезу пометить.>

### План реализации

### Образцы и похожие задачи

### Критерии приёмки
- [ ] ...

### Как проверить

```

**Жди ответа.** Пользователь скажет «ок» / поправит / откажется.

### Фаза 6 — Создание задачи

После «ок»:
1. `mcp__atlassian__jira_create_issue` с согласованными полями и текстом
2. Есть исходная задача — `jira_create_issue_link`
3. В проекте используется smart checklist — критерии приёмки через `jira_replace_smart_checklist`
4. Ответь одной строкой: ключ и ссылка

Atlassian недоступен — выдай текст задачи в чат в готовом для копирования виде и скажи, что задача не создана.

## ЗАПРЕТЫ

- ❌ Изменять файлы выгрузки, вызывать load-операции (`/1c-batch load-*`)
- ❌ Любой SQL, кроме SELECT (в том числе `EXEC` хранимых процедур); запросы без `TOP` к большим таблицам (регистры, движения)
- ❌ Создавать задачу, добавлять комментарии или менять статус в Jira без согласования текста
- ❌ Выдавать гипотезу за установленную причину
- ❌ Писать в задаче готовую реализацию вместо плана
- ❌ Спрашивать пользователя о том, что можно найти в конфигурации, данных или Jira самому
- ❌ Делать вывод «кода нет», не проверив выгрузку и кеш обычных форм
