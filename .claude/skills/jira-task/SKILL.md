# /jira-task — Анализ → Черновик → Согласование → Jira

Скилл оформляет результат анализа в Jira. Три режима:

| Режим | Когда (слова пользователя) | Действие |
|---|---|---|
| **Создать** | «поставь / создай / заведи / оформи задачу», «сделай баг на разработчика» | `jira_create_issue` (+ связь, + чек-лист) |
| **Комментарий** | «добавь комментарий», «допиши в KEY», «отпиши в задаче», «напиши разработчику в KEY» | `jira_add_comment` |
| **Обновить** | «обнови / измени / дополни задачу KEY», «поменяй описание / заголовок», «добавь критерии приёмки», «свяжи с KEY» | `jira_update_issue` / `jira_create_issue_link` / `jira_replace_smart_checklist` |

Режим определяй по словам пользователя. Неоднозначно («сделай что-то с KEY») — один вопрос через AskUserQuestion:
комментарий / обновить описание / новая задача.

## Принципы

- **Делает только то, что попросили.** Попросили комментарий — не создавай задачу и не меняй описание. Статус, исполнитель,
  спринт, приоритет — только если пользователь назвал их явно
- **Одна точка согласования** — полный текст изменения. После «ок» — выполнить без дополнительных вопросов
- **Изменения — только после «ок».** Правки пользователя → показать исправленный текст ещё раз
- **Содержание — из анализа.** Источник фактов — анализ `/analyze` в этом разговоре. Новых выводов здесь не делаем

## Процесс

### Шаг 1 — Есть ли анализ

- В разговоре есть результат `/analyze` (или эквивалентный анализ с доказательствами) — используй его
- Анализа нет, а пользователь даёт готовый текст («добавь в KEY комментарий: ...») — оформляй его текст как есть,
  без исследования
- Анализа нет и текста нет («поставь задачу на исправление X») — скажи одной строкой, что сначала нужен анализ,
  и вызови `/analyze`; по его завершении продолжи с Шага 2 (это явная просьба пользователя, поэтому переход допустим)

### Шаг 2 — Контекст в Jira

- Режимы **Комментарий / Обновить**: `jira_get_issue` по ключу — текущее описание, комментарии, статус, связи
  (чтобы не повторять уже написанное и показать, что именно меняется)
- Режим **Создать**: проверь дубли — открытые задачи по тем же объектам (`jira_search`,
  `statusCategory != Done AND text ~ "<объект>"`). Нашлась похожая — покажи её и спроси одним вопросом:
  создать новую / добавить комментарий в найденную. Неизвестны проект или тип — уточни (`jira_get_all_projects`)

### Шаг 3 — Черновик (ЕДИНСТВЕННАЯ точка согласования)

Покажи **полный текст одним сообщением** по шаблону режима. Внизу — одна строка: что будет сделано
(«Создам задачу в проекте X» / «Добавлю комментарий в KEY» / «Заменю описание KEY»).

**Создать:**

```markdown
**Проект:** <KEY>   **Тип:** <Bug / Task / Story>   **Связь:** <relates to ABC-123>
**Заголовок:** <Объект: что сделать/исправить — до 80 символов>

### Контекст
<Кто, в каком сценарии, зачем. Ссылка на исходное обращение.>

### Как сейчас
<Сценарий и его реализация: Объект → Модуль → Процедура. Для ошибки — шаги воспроизведения,
фактический и ожидаемый результат.>

### Что нужно
<Целевое поведение глазами пользователя. Для ошибки — причина: где в коде и почему; гипотезу пометить.>

### План реализации
1. <Объект → Модуль/Форма → Процедура>: <что изменить и зачем>
2. <Метаданные: новый реквизит/регистр/значение перечисления — имя, тип>
3. <Форма: какой элемент, на какой странице; обычная форма — «в конфигураторе»>
4. <Права/интерфейс: какие роли и интерфейсы (меню) затронуть>

<Без готового кода; псевдокод — если упрощает понимание.>

### Критерии приёмки

### Как проверить
<Документ/элемент в тестовой базе, шаги, SQL-запрос для контроля данных.>
```

**Комментарий:** короткий текст для разработчика/аналитика — только то, что нового дал анализ
(причина, где в коде, уточнение плана, ответ на вопрос из задачи). Не дублируй описание задачи.

```markdown
**Комментарий в <KEY>:**

<Вывод в 1–3 предложениях — [установлено | гипотеза]>

**Где:** <Объект → Модуль → Процедура>, <фрагмент 3–10 строк, если нужен>
**Что предлагается:** <пункты плана или ответ>
**Проверка:** <как убедиться> (если применимо)
```

**Обновить:** покажи **что меняется** — поле и новое значение. Для описания — весь новый текст и кратко,
что добавлено/изменено относительно текущего (добавляемые разделы, исправленные пункты). Существующий текст
не удаляй и не переписывай без просьбы пользователя — дополняй.

**Жди ответа.** «ок» → Шаг 4. Правки → исправленный текст ещё раз. Отказ → завершить без изменений.

### Шаг 4 — Выполнение (после «ок»)

| Режим | Вызовы |
|---|---|
| Создать | `mcp__atlassian__jira_create_issue`; есть исходная задача — `jira_create_issue_link`; в проекте используется smart checklist — критерии приёмки через `jira_replace_smart_checklist` |
| Комментарий | `mcp__atlassian__jira_add_comment` |
| Обновить | `mcp__atlassian__jira_update_issue` (поля/описание); связь — `jira_create_issue_link`; чек-лист — `jira_replace_smart_checklist` / `jira_update_smart_checklist` |

Ответь одной строкой: что сделано, ключ и ссылка.

Atlassian недоступен — выдай согласованный текст в чат в готовом для копирования виде и скажи, что в Jira ничего не изменено.

## ЗАПРЕТЫ

- ❌ Любая запись в Jira до «ок» на показанный текст
- ❌ Делать больше, чем попросили: создавать задачу вместо комментария, менять описание вместо комментария,
  менять статус / исполнителя / спринт / приоритет без явной просьбы
- ❌ Удалять или переписывать существующий текст описания и чужие комментарии без явной просьбы
- ❌ Добавлять в текст выводы, которых нет в анализе; выдавать гипотезу за установленную причину
- ❌ Писать готовую реализацию вместо плана
- ❌ Исследовать код/данные заново — это `/analyze`
