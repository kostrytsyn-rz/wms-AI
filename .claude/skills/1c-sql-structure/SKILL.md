# Структура конфігурації 1С ↔ SQL-база

Є два джерела, обидва через MCP:

| Джерело | MCP-інструменти | Що дає |
|---|---|---|
| Конфігурація 1С (метадані, код) | `mcp__1c-rag__list_metadata_objects`, `mcp__1c-rag__get_object_metadata`, `mcp__1c-rag__search_1c_objects` | Логічна структура: реквізити, виміри, ресурси, табличні частини, **типи** полів |
| SQL-база (MSSQL) | `mcp__mssql-mcp__query_sql`, `mcp__mssql-mcp__list_tables` | Дані. Фізичні таблиці мають службові імена (`_InfoRg326`, `_Fld328RRef`), але для них створено **view з людськими іменами** |

**Головне правило: запити пиши до view, а не до фізичних таблиць `_...`.** До службових таблиць звертайся лише якщо view для об'єкта немає (див. «Якщо view немає»).

## Іменування view

Ім'я в конфігурації `Тип.Имя` → view `dbo.[Тип_Имя]` (крапка замінюється на `_`, тип в однині):

| Конфігурація | View | Фізична таблиця (приклад) |
|---|---|---|
| `Справочник.Номенклатура` | `dbo.Справочник_Номенклатура` | `_Reference11` |
| `Документ.Счет` | `dbo.Документ_Счет` | `_Document32` |
| `Документ.Счет.ТабличнаяЧасть.Товары` | `dbo.Документ_Счет_Товары` | `_Document32_VT286` |
| `РегистрСведений.Товары` | `dbo.РегистрСведений_Товары` | `_InfoRg326` |
| `Перечисление.СтатусыЗаказа` | `dbo.Перечисление_СтатусыЗаказа` | `_Enum40` |
| `ПланВидовХарактеристик.ЗначенияПоУмолчанию` | `dbo.ПланВидовХарактеристик_ЗначенияПоУмолчанию` | — |

Табличні частини: `Тип_Объект_ИмяТЧ`. Імена кирилицею — завжди бери їх у квадратні дужки або пиши як є, без лапок-ялинок.

Знайти view: `SELECT name FROM sys.views WHERE name LIKE N'%Номенклат%'`.
Подивитись колонки: `SELECT name FROM sys.columns WHERE object_id = OBJECT_ID(N'dbo.Справочник_Номенклатура')`.
Подивитись, з чого зроблено view: `SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.РегистрСведений_Товары'))`.

### Інші об'єкти в базі (не з конфігурації)
- `..._АРХ` (`Документ_Счет_АРХ`, `РегистрСведений_Товары_АРХ`…) — **таблиці** з архівними даними. Не забувай про них, якщо питають про історію.
- View без префікса типу (`ТоварВАдресеОстаток`, `ТоварСНОстаток`, `ТоварУСотрудника`, `РезервАТ`, `ЯрусАдресВес`…) — агрегати/індексовані view поверх регістрів. Перед використанням прочитай `OBJECT_DEFINITION`, щоб знати фільтри (напр. `ТоварВАдресеОстаток` = сума `РегистрСведений_Товары` лише з `Документ_TYPE = 0x08`).
- `_InfoRg1725` тощо — «зворотні» view, що імітують службову таблицю поверх людських view. Не використовуй їх у своїх запитах.
- `Config*`, `Params`, `v8users`, `DBSchema`… — службові таблиці платформи, не чіпати.

## Стандартні колонки у view

**Справочник**: `Ссылка`, `ВерсияДанных`, `ПометкаУдаления`, `ИмяПредопределенныхДанных`, `Родитель`, `ЭтоГруппа`, `Наименование`, (`Код`, `Владелец` — якщо є) + реквізити.
**Документ**: `Ссылка`, `ВерсияДанных`, `ПометкаУдаления`, `Дата`, `Номер`, `Проведен` + реквізити.
**Табличная часть**: `Ссылка` (= посилання на власника), `НомерСтроки`, `_KeyField` + реквізити ТЧ.
**РегистрСведений**: `Период` (якщо періодичний), виміри, ресурси, реквізити. (`Регистратор` — якщо підпорядкований регістратору.)
**Перечисление**: `Ссылка`, `Порядок`, `Значение` (ім'я значення, напр. `'Отгружен'`).

## Посилальні поля та з'єднання

Поле посилального типу (`Справочник.X`, `Документ.X`, `Перечисление.X`) у view — це `binary(16)` з ім'ям реквізиту. З'єднуй із полем `Ссылка` відповідного view:

```sql
SELECT TOP 100 С.Номер, С.Дата, К.Наименование AS Контрагент, Ст.Значение AS Статус
FROM dbo.Документ_Счет С
LEFT JOIN dbo.Справочник_Контрагенты      К  ON К.Ссылка  = С.Контрагент
LEFT JOIN dbo.Перечисление_СтатусыЗаказа  Ст ON Ст.Ссылка = С.Статус
WHERE С.Проведен = 0x01
ORDER BY С.Дата DESC;
```

**Тип реквізиту дізнавайся з конфігурації** (`get_object_metadata`) — у SQL видно лише `binary(16)`, а на який довідник/документ посилання, знає тільки метадані. Напр. `РегистрСведений.Товары.Товар` — `Справочник.Номенклатура`, `Сотрудник` — `Справочник.Сотрудники`.

Табличну частину з'єднуй з шапкою через `Ссылка`:
```sql
SELECT С.Номер, Т.НомерСтроки, Н.Наименование, Т.Количество, Т.Сумма
FROM dbo.Документ_Счет С
JOIN dbo.Документ_Счет_Товары   Т ON Т.Ссылка = С.Ссылка
LEFT JOIN dbo.Справочник_Номенклатура Н ON Н.Ссылка = Т.Товар
WHERE С.Номер = N'РОЗ629772012';
```

Перелічення фільтруй через view перелічення, не через «магічні» байти:
```sql
WHERE С.Статус = (SELECT Ссылка FROM dbo.Перечисление_СтатусыЗаказа WHERE Значение = 'Отгружен')
```

Пусте посилання = `0x00000000000000000000000000000000`.

## Складені типи (реквізит з кількома типами)

Розкладаються на кілька колонок з суфіксами:
- `Имя_TYPE` — вид значення: `0x01` = Неопределено/порожньо, `0x08` = посилання (також бувають `0x02` булево, `0x03` число, `0x04` дата, `0x05` рядок; тоді є колонки `Имя_L`, `Имя_N`, `Имя_T`, `Имя_S`). У цій базі трапляються рядки з `_TYPE = 0x00` — не покладайся лише на `_TYPE`, перевіряй `_RTRef`.
- `Имя_RTRef` — `binary(4)`, номер таблиці об'єкта, на який посилання. `CAST(Имя_RTRef AS int)` = `ИдентификаторТаблицы` у `СоответствияТаблиц` (напр. 30 → `Документ.ПриходнаяНакладная`, 31 → `Документ.Перемещение`, 29 → `Документ.СчетВходящий`).
- `Имя_RRRef` — `binary(16)`, саме посилання (= `Ссылка` у view цього об'єкта).

```sql
SELECT Т.Адрес, Т.Количество, П.Номер AS НомерПеремещения
FROM dbo.РегистрСведений_Товары Т
JOIN dbo.Документ_Перемещение П ON П.Ссылка = Т.Документ_RRRef
WHERE Т.Документ_RTRef = (SELECT CAST(ИдентификаторТаблицы AS binary(4))
                          FROM dbo.СоответствияТаблиц
                          WHERE ТипТаблицы = 'Документ' AND ПредставлениеТаблицы = 'Перемещение');
```

## Дати: зсув +2000 років

База 1С створена зі зсувом дат: **рік у SQL = реальний рік + 2000** (`4026-10-30` = 30.10.2026). Порожня дата = `2001-01-01 00:00:00`.
- Фільтр: `WHERE Дата >= '4026-10-01' AND Дата < '4026-11-01'` (або `DATEADD(year, 2000, @d)`).
- Вивід користувачу: `DATEADD(year, -2000, Дата) AS Дата`.
- Ніколи не порівнюй з `GETDATE()` напряму — тільки `DATEADD(year, 2000, GETDATE())`.

## Інші типи
- Булево — `binary(1)`: `0x01` = Истина, `0x00` = Ложь (`Проведен = 0x01`, `ПометкаУдаления = 0x00`).
- Рядки — `nvarchar`/`nchar` (nchar доповнений пробілами: використовуй `RTRIM` або `LIKE`). Рядкові літерали з кирилицею — з префіксом `N'...'`.
- Число — `numeric`.

## Таблиці відповідностей (словник метаданих у SQL)

| Таблиця | Призначення |
|---|---|
| `dbo.СоответствияТаблиц` | `ИдентификаторТаблицы`, `ТипТаблицы` (`Справочник`, `Документ`, `РегистрСведений`, `Перечисление`, `Справочник.ТабличнаяЧасть`…), `ИмяТаблицы` (`_Reference11`), `ПредставлениеТаблицы` (ім'я в конфігурації), `ИдентификаторВладельцаТаблицы` (для ТЧ) |
| `dbo.СоответствияПолей` | `ИдентификаторТаблицы`, `ИмяКолонки` (`_Fld328RRef`), `ПредставлениеКолонки` (`Товар`), `ПредставлениеТипаКолонки` (інколи — ім'я типу) |
| `dbo.СоответствияПеречислений` | значення перелічень: `ЗначениеПеречисления` (binary) ↔ `ИмяПеречисления`, `СинонимПеречисления` |
| `dbo.СоответствияПредопределенных` | предопределені елементи: `ИмяПредопределенногоЗначения`, `МетаданныеТип`, `МетаданныеИмя`, `СсылкаПредопределенного` |

Розшифрувати службове ім'я:
```sql
SELECT Т.ТипТаблицы, Т.ПредставлениеТаблицы, П.ПредставлениеКолонки
FROM dbo.СоответствияТаблиц Т
LEFT JOIN dbo.СоответствияПолей П ON П.ИдентификаторТаблицы = Т.ИдентификаторТаблицы AND П.ИмяКолонки = '_Fld328RRef'
WHERE Т.ИмяТаблицы = '_InfoRg326';
```

## Збережені процедури, функції, тригери (бізнес-логіка в SQL)

Частина логіки WMS виконується **в SQL, а не в 1С**: ~296 процедур, ~44 функції, 1 тригер (`wms_preprod`, перевірено 2026-11-09).
Процедури пишуть прямо у view регістрів (напр. `АвтоСортировкаПеремещений_*` оновлює `РегистрСведений_ТЧСортировки`),
тобто змінюють дані 1С поза механізмами платформи. 1c-rag цих процедур не бачить — текст доступний **лише** через `mssql-mcp`.

### Як 1С їх викликає

- Через ADO: `МодульSQL.ВыполнитьЗапрос(<T-SQL>, ...)` / `МодульSQL.ВыполнитьКоманду(...)` → `ADODB.Command`.
  У тексті — `exec [dbo].[ИмяПроцедуры] @Параметр = ...` або цілий T-SQL-пакет, зібраний рядком у модулі.
- Знайти виклики конкретної процедури: Grep `ИмяПроцедуры` по `configuration\` **і** `.formbin-cache\` (`glob: *.bsl`).
  Усі виклики: Grep `(?i)exec\s+\[?dbo` — ~174 входження у 55 модулях (більше за все — `СРРегламентныеЗадания`,
  `РегистрыСведений.ТЧСортировки`, `ОперацииСклада`, `ВолныСборки`, АРМи відвантаження/приймання/сортування).
- Деякі процедури **створюються з 1С** (`РегистрыСведений.ТЧСортировки.Создать_SP_<Имя>`): тоді текст є і в модулі 1С,
  і в базі — порівнюй, чи не розійшлися.

### Запити

```sql
-- перелік (найсвіжіші зміни зверху)
SELECT o.name, o.type_desc, CONVERT(varchar(10), o.modify_date, 120) AS modified, LEN(m.definition) AS len
FROM sys.objects o JOIN sys.sql_modules m ON m.object_id = o.object_id
WHERE o.type IN ('P','FN','IF','TF','TR') AND o.name LIKE N'%Сортир%'
ORDER BY o.modify_date DESC;

-- текст (довгі процедури — шматками по 8000, щоб не забивати контекст)
SELECT LEN(OBJECT_DEFINITION(OBJECT_ID(N'dbo.ИмпортТоваров'))) AS len;
SELECT SUBSTRING(OBJECT_DEFINITION(OBJECT_ID(N'dbo.ИмпортТоваров')), 1, 8000);

-- параметри
SELECT name, TYPE_NAME(user_type_id) AS type, max_length, is_output
FROM sys.parameters WHERE object_id = OBJECT_ID(N'dbo.АвтоСортировкаПеремещений_Обычных') ORDER BY parameter_id;

-- що процедура читає/пише (таблиці, view, інші процедури)
SELECT DISTINCT referenced_entity_name
FROM sys.sql_expression_dependencies WHERE referencing_id = OBJECT_ID(N'dbo.ИмпортТоваров');

-- хто в SQL використовує view/таблицю (аналіз впливу на рівні SQL)
SELECT DISTINCT OBJECT_NAME(referencing_id) AS obj
FROM sys.sql_expression_dependencies WHERE referenced_entity_name = N'РегистрСведений_ТЧСортировки';

-- текстовий пошук по всіх процедурах/функціях
SELECT o.name FROM sys.sql_modules m JOIN sys.objects o ON o.object_id = m.object_id
WHERE m.definition LIKE N'%РНОтгрузки%';
```

`sql_expression_dependencies` не бачить динамічний SQL (`exec(@sql)`) і тимчасові таблиці — для них текстовий пошук.

### Обмеження

- База — **preprod**: процедури на продуктиві можуть відрізнятися. У задачі вказуй, що текст узято з preprod, і дату `modify_date`.
- Процедури тільки **читаємо**: не виконуй `EXEC` — більшість змінює дані.
- Зміна процедури — окремий пункт плану реалізації («змінити `dbo.<Имя>` на SQL-сервері»), бо вона не входить у `.cf` і не
  розгортається разом із конфігурацією.

## Порядок роботи

1. Зрозумій, про які об'єкти конфігурації йдеться: `search_1c_objects` / `list_metadata_objects(object_type=..., name_filter=...)`.
2. Візьми структуру й **типи полів**: `get_object_metadata(object_type, object_name)`.
3. Знайди view і звір колонки (`sys.columns`). Імена колонок view збігаються з іменами реквізитів у конфігурації.
4. Склади запит до view з JOIN по `Ссылка`, урахуй зсув дат, булеві `0x01/0x00`, складені типи.
5. Запити тільки на читання; на великих таблицях завжди `TOP N` та фільтр за датою/ключем, бажано `WITH (NOLOCK)` — це база з робочими даних WMS (великі обсяги).
6. У відповіді користувачу показуй дати без зсуву і називай об'єкти іменами конфігурації (`РегистрСведений.Товары`), а не службовими.

## Якщо view немає

1. `SELECT * FROM dbo.СоответствияТаблиц WHERE ПредставлениеТаблицы = N'ИмяОбъекта'` → `ИмяТаблицы`.
2. `SELECT ИмяКолонки, ПредставлениеКолонки FROM dbo.СоответствияПолей WHERE ИдентификаторТаблицы = <id>` → карта колонок.
3. Пиши запит до `_...`-таблиці, але задавай колонкам аліаси з іменами реквізитів (`_Fld328RRef AS Товар`) і скажи користувачу, що view для об'єкта немає.
